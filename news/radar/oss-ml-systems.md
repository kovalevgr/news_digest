## 2026-W34

- **2026-08-18** — [Advanced CUDA Graph Techniques in SGLang](https://lmsys.org/blog/2026-08-17-advanced-cuda-graph) — Verified via WebFetch: SGLang's three CUDA-graph backends — full-graph capture, Breakable CUDA Graph (BCG, segments capture with eager breaks around incompatible ops instead of paying torch.compile cost), and TC Piecewise (torch.compile trace+split) — with measured numbers: BCG builds 3.8–5.2× faster than compiler-based piecewise (torch.compile alone was 78–86% of prefill-graph prep time), replay-latency speedups of 1.93× (full capture), 1.70× (BCG) and 1.45× (TC piecewise) vs eager, activation-memory peaks cut from 0.56GB to 0.001GB via chunked-prefill-size capture, and end-to-end diffusion latency down from 6.48s to 2.45s.
- **2026-08-18** — [Miles v0.1: Production-level Post-training](https://lmsys.org/blog/2026-08-18-miles-v0-1) — Verified via WebFetch: full-stack RL post-training system (rollout via SGLang, training via Megatron-LM/FSDP) with Token-In-Token-Out fidelity, Rollout Routing Replay for MoE numerical stability, NVFP4/MXFP8/FP8 training, and NVMe optimizer-state offload. Concrete numbers: GLM-5.2 744B trains on 64 GB300 GPUs at 96% prefix-cache hit rate; on-policy distillation cut Qwen3.5-35B rollout length 18.6K→~6K tokens while improving held-out accuracy 84.6%→89.5%; P2P weight sync for Kimi-K2 1T cut update time 53.3s→7.2s (disk-delta payload 62.4GB→0.69–0.83GB); day-0 support across NVIDIA A100–GB300 and AMD MI300X–MI355X.
- **2026-08-19** — [Pushing the Limits of Serving DeepSeek-V4-Pro](https://lmsys.org/blog/2026-08-19-deepseek-v4-pro-engine-optimization-h20) — Verified via WebFetch: SGLang optimizations for serving DeepSeek-V4-Pro on 8×H20 GPUs (which lack native FP4 tensor cores) — Humming MXFP4×FP8 (MXFP4 expert weights + online FP8 activations), Online C128 KV-cache compression, MoE-TP instead of MoE-EP for predictable prefill traffic, and DSpark speculative decoding extended across pipeline stages. Concrete numbers: 31.8% geomean prefill throughput gain (25,860 tok/s at 512K context, PP4-CP8-TP8); DSpark cuts peak per-token decode latency 74.8–78.0% at batch size 1, reaching 271 tok/s vs. a B300 reference's 383.7 tok/s (1.42× the throughput-per-compute despite a 45.6× compute gap); Humming+Online C128 expands full-token capacity 3.88–10.14×; per-GPU decode throughput up 2.20× (319.92→703.15 tok/s/GPU, DP32-EP32, 4K ctx, 32 concurrent requests).
- **2026-08-20** — [Mooncake for Miles: From Fragmented Rollout Data to Efficient Bulk I/O](https://lmsys.org/blog/2026-08-20-miles-mooncake-rollout-data-transfer) — Verified via WebFetch: follow-up to Miles v0.1 (2026-08-18) — Mooncake (a high-performance data plane for distributed AI) replaces Miles's Ray-based rollout-to-training transfer, preserving heterogeneous field structure (dense tensors, ragged sequences, scalars, Python objects) while converting thousands of fragmented per-row NumPy allocations into bulk I/O via a registered buffer pool, behind a simple `put`/`get` interface. On fragmented Qwen3-0.6B rollout data (~3,422 bytes/sample): GET ~10–14× faster than the Ray backend, PUT ~1.2–1.6× faster, gains growing with payload size — no change to Miles's RL programming model.
- **2026-08-20** — [Harnessing AI for Day-One Model Enablement](https://pytorch.org/blog/harnessing-ai-for-day-one-model-enablement/) — Verified via WebFetch: PyTorch/IBM post on using coding agents to write "adapters" — runtime patches that swap an unsupported op for a mathematically-identical one, or reshape tensor data (e.g. padding a vocab dimension so a matmul divides evenly across cores) — bridging stock HuggingFace Transformers models onto IBM's new Spyre AI accelerator (torch-spyre backend) without waiting for the compiler stack to mature; the model's math is provably unchanged (bit-identical on CPU/GPU), only its lowered form changes. Agents handle the wide cross-referencing (tracing a model's logic against the compiler's lowering code, drafting patches by analogy to prior adapters); humans handle localization of silent on-device failures and distrust of single-experiment conclusions — flagged as a recurring failure mode where a scary intermediate-tensor discrepancy turns out harmless once traced to the actual output. Concrete result: 13 distinct adapters (built over a few months) cover 7,960 of the 10,000 most-downloaded HF embedding models, 6,804 of which pass end-to-end on-device tests; code in `torch-spyre/hf-adapters` and `torch-spyre/torch-spyre` (both public on GitHub).
